## 1. 项目定义

### 1.1 一句话定位

> **bike-hub 是安装在自行车车架上的联网智慧中枢：以"防丢防盗"为切入点，把"联网 + 定位 + 感知"沉淀成可复用的能力，最终扩展为骑行码表与运动数据终端。**

这是两条曲线，不是两个产品：

- **第一曲线（0 → 1）**：防盗。真实痛点、高频恐惧、可快速验证付费意愿。
- **第二曲线（1 → N）**：码表 / 骑行记录。复用同一套硬件与云，边际成本极低。

### 1.2 为什么这个顺序是对的

防盗场景倒逼出三个"高标准能力"，而这三个能力恰好是码表场景的基础设施：

| 防盗场景的要求 | 对应的底层能力 | 码表场景的复用方式 |
| --- | --- | --- |
| 车被搬走时能持续上报位置 | 低功耗 4G 长连接 + 高频率 GNSS | 骑行轨迹录制 |
| 设备要装在车里、不能被轻易拆 | 车架贴合外壳 + 防水 + 供电设计 | 全天候外置设备形态 |
| 电池要撑住一个月以上的"待机" | 极低功耗调度 + 硬件中断唤醒 | 长距离骑行的续航底座 |

反过来则不成立：先做码表，很难自然地长出防盗能力（码表不防拆、不需要长期待机、不需要多点告警）。**所以"先防盗、后码表"不只是叙事顺序，也是技术复用顺序。**

### 1.3 产品边界

- **是**：独立的、后装的、可迁移的第三方设备；贴车架、隐蔽、自带电池与网络。
- **不是**：智能锁（不改动原有锁具）、整车内置方案（不绑定某一品牌车架）、纯蓝牙防丢器（不依赖手机或人群网络）。

## 2. 原始需求还原与拆解

把口述需求逐句拆成可判定的需求项，避免"听起来都懂、落地都含糊"。

| # | 原始表述 | 拆解出的需求项 | 隐含约束 |
| --- | --- | --- | --- |
| R1 | 安装在自行车上的智慧中枢 | 独立硬件设备，可安装于车架 | 体积、重量、外观、安装兼容性 |
| R2 | 一开始只是想做防自行车被盗的装置 | 首发定位是防盗 | 不能一开始就摊大功能 |
| R3 | 通过各种传感器识别车辆被动手脚的风险 | 多传感器 + 本地风险判定 | 低误报是第一难题 |
| R4 | 通过喇叭播放警报 | 现场声学威慑 | 声压级、功耗峰值、扰民/误报 |
| R5 | 发通知到手机 | 远程告警链路 | 低时延、高到达率、断网兜底 |
| R6 | 手机可以通过语音方式警告 | 远程语音干预（对讲 / 播报） | 通信带宽、成本、合规 |
| R7 | 带有定位，手机可查询位置 | GNSS 定位 + 地图展示 | 精度、功耗、室内失效 |
| R8 | 3D 打印贴合车架的外壳 | 形态贴合 + 差异化外观 | SKU、量产工艺、防水、散热 |
| R9 | 未来做码表和运动轨迹、表现记录 | 第二曲线功能 | V1 硬件与架构要为 V2 预留 |

**关键观察**：R3、R4、R5、R6 共同构成一个完整的"**感知 → 判定 → 威慑 → 干预**"闭环，而不是四个独立功能。这个闭环的强度决定了产品是否真的"有用"，而不是"有个 App 能看到车在哪"。

## 3. 核心产品假说

这三条假说决定了后续所有取舍，建议任何功能评审都拿它们当尺子。

### H1：防盗产品的胜负手是"误报率"，不是"检测灵敏度"

一个每天误报两次的防盗器，用户第三天就会关掉它——此时产品价值归零。**宁可漏报一次，也不要把误报率做到无法容忍。** 行业经验是：误报率（每用户每周）< 0.2 次，才可能被长期开启。

推论：

- 必须做多传感器交叉验证，不能靠单一震动阈值。
- 必须有"分级响应"：轻微 → 本地短提示；确认 → 推送；高危 → 全量警报。而不是一有震动就 110 dB。
- 必须支持地理围栏与"手机在场自动撤防"，否则在家充电、在车库被碰一下都会吼。

### H2：用户要的不是"坐标"，而是"把车拿回来"的过程体验

只给一个地图上的点，用户到现场依然找不到车（尤其在楼道、车库、车辆堆里）。**找回体验 = 最后 10 米的引导 + 过程中的持续威慑。** 这是多数 GPS 追踪器做得最差的一环，也是差异化的机会。

推论：需要"寻车模式"——近场 BLE 测距 + 声光提示 + 实时追踪节流策略，而不仅是定时上报坐标。

### H3：语音干预是"确认 + 威慑"的组合动作，不是对讲机

远程喊话的真实价值有两层：

1. **威慑**：让小偷知道"车主已经看到了"，比警报声更有效（警报已经被社会性免疫）。
2. **确认**：让用户在按下警报前，先听/看一眼，避免误判邻居挪车而尴尬。

推论：V1 不需要高保真双向通话，需要的是"**低延迟、够清楚、按一下就能喊**"。这大幅降低了研发成本（见 §7.4）。

## 4. 用户与场景

### 4.1 目标用户（按优先级）

| 优先级 | 画像 | 核心诉求 | 付费意愿 | 对产品的额外要求 |
| --- | --- | --- | --- | --- |
| P0 | 城市通勤者（车价 2k–8k） | 楼下/地铁口停车不放心 | 中 | 便宜、不显眼、装一次不用管 |
| P0 | 运动骑行爱好者（车价 8k–50k） | 高端车不敢离开视线 | 高 | 隐蔽、轻、不破坏车、未来能当码表 |
| P1 | 共享/租赁/车队运营 | 车辆资产管理与丢失追回 | 高（B 端） | 批量管理、API、长续航 |
| P2 | 家长（儿童车） | 孩子骑行范围 | 中 | 电子围栏、低功耗 |

**建议首发聚焦 P0 的两类个人用户**，B 端作为第二阶段的商业放大。

### 4.2 关键场景（Scene）

| ID | 场景 | 触发 → 系统行为 | 成功标准 |
| --- | --- | --- | --- |
| S1 | 路边停车，路人碰倒/挪车 | 短时冲击 → 本地短提示音，不上报或合并上报 | 不打扰用户 |
| S2 | 撬锁 / 剪锁 | 高频冲击 + 持续振动 → 本地警报 + 推送 + 录音片段 | 用户 10 s 内收到 |
| S3 | 整车被抬走 | 倾角+加速度特征 + 位移 → 强警报 + 实时追踪 | 可持续追踪 ≥ 24 h |
| S4 | 推出地理围栏（非授权移动） | 围栏穿越 + 无授权手机在场 → 强警报 + 实时追踪 + 语音通道就绪 | 第一时间可喊话 |
| S5 | 被装进面包车 / 信号屏蔽袋 | 心跳超时 / 信号骤降 → "失联告警" + 最后位置 + 历史轨迹 | 失联本身即告警 |
| S6 | 车主自己挪车 | 手机 BLE 在场 → 自动撤防，零打扰 | 零误报 |
| S7 | 用户收到告警后远程喊话 | App 一键语音 → 设备喇叭外放 → 小偷放弃 | 建立语音 < 2 s |
| S8 | 用户到现场找车 | 寻车模式 → 近场 BLE 测距 + 声光提示 | 10 m 内可定位 |
| S9 | 设备被拆 / 断电 | 防拆开关 + 掉电记录 → 拆机告警（用备用电源发出） | 拆机也能告警 |
| S10 | 日常骑行（V2） | 自动识别骑行 → 记录轨迹/速度/里程 | 免手动开始 |

**场景 S5、S9 是大多数竞品的盲区**：它们只在"设备活着且联网"时有效，而现实中盗贼的第一动作往往就是屏蔽或拆机。把"失联"和"被拆"当成一等告警信号，是本产品应该有的对抗性设计。

### 4.3 威胁模型（Threat Model）

防盗产品必须假设对手是理性的：

| 攻击方式 | 设备的检测手段 | 对抗设计 |
| --- | --- | --- |
| 抬走整车 | 加速度/倾角 + GNSS 位移 + 围栏 | 静默上报（先不打草惊蛇）+ 强警报可远程触发 |
| 撬/剪锁 | 冲击频谱特征 + 持续时间 | 本地先响（不依赖网络），再上报 |
| 拆设备 | 防拆微动开关 + 外壳霍尔 + 断线检测 | 备用小电池维持告警 30 s；拆机事件落盘 |
| 信号屏蔽（法拉第袋/jammer） | 心跳超时 + RSSI 骤降 | 失联告警 + 本地继续响 |
| 拔电池/短路 | 电源路径检测 + 掉电日志 | 后备电源 + 超级电容保告警 |
| 拆天线 | 天线检测（驻波/开短路） | 天线故障告警 |
| 破坏外壳 | 结构设计 + 隐蔽安装位置 | 低可见度、异形螺丝、灌封 |

> **设计原则：告警的"本地闭环"必须先于"云端闭环"。** 断网时必须能响；联网只负责"让人知道"和"能干预"。

## 5. 功能需求（FR）

优先级定义：**P0** = MVP 必须有，缺失则产品不成立；**P1** = 首个量产版本应有；**P2** = 后续迭代。

### FR-1 布防与状态管理

| ID | 需求 | 优先级 | 验收标准 |
| --- | --- | --- | --- |
| FR-1.1 | 手动布防/撤防（App、物理按键可选） | P0 | 操作后 2 s 内状态同步到设备与云端 |
| FR-1.2 | 自动布防：静止 N 分钟后进入布防 | P0 | N 可配置，默认 3 min |
| FR-1.3 | 自动撤防：手机 BLE 在场（授权设备） | P0 | 进入 3 m 内 10 s 内撤防，不产生告警 |
| FR-1.4 | 地理围栏：家/公司等白名单区域降低灵敏度或延迟告警 | P1 | 支持自定义围栏与"宽限期"（默认 90 s） |
| FR-1.5 | 多用户共享车辆（家人共骑） | P1 | 邀请/移除成员，权限分级 |
| FR-1.6 | 布防状态与灵敏度档位可调（低/中/高） | P1 | 档位影响判定阈值，App 可实时调整 |

### FR-2 传感器感知与风险判定（核心）

| ID | 需求 | 优先级 | 验收标准 |
| --- | --- | --- | --- |
| FR-2.1 | 6 轴 IMU 感知震动、冲击、倾角变化 | P0 | 可区分"轻碰"与"持续撬动"，采样与中断配置满足低功耗 |
| FR-2.2 | 车轮转动检测（霍尔+磁铁） | P0 | 车轮转动 ≥ 1 圈可识别，用于区分"推行"与"原地撬" |
| FR-2.3 | 位移检测（GNSS 位移 / 基站变化） | P0 | 静止判定下位移 > 15 m 触发 |
| FR-2.4 | 多传感器融合的风险状态机（见 §5.1） | P0 | 分级判定，误报率达标（见 NFR-6） |
| FR-2.5 | 光感：外壳被打开/被遮挡 | P1 | 开盖 1 s 内识别 |
| FR-2.6 | 气压计：判断被搬入地下/楼层变化（辅助） | P2 | 作为位移与场景判断的辅助特征 |
| FR-2.7 | 声音事件识别（玻璃破碎/工具声） | P2 | 误报率可控后再上线 |

#### 5.1 风险分级状态机（建议）

```
        ┌────────┐   静止 3 min   ┌────────┐  轻碰/单次冲击  ┌────────┐
        │  S0    │ ─────────────► │  S1    │ ──────────────► │  S2    │
        │ 睡眠   │                │ 布防   │ ◄────────────── │ 疑似   │
        └────────┘                └────────┘   30 s 无后续   └────────┘
             ▲                        │                          │ 多传感器确认
             │ 撤防/授权在场           │ 位移>15m / 围栏穿越        │ 或持续>10s
             │                        ▼                          ▼
        ┌────────┐                ┌─────────────────────────────────┐
        │  S5    │ ◄── 手动撤防 ── │  S3 确认威胁                     │
        │ 撤回   │                 │ 本地警报 + 推送 + 追踪 + 语音就绪 │
        └────────┘                 └─────────────────────────────────┘
```

- **S1 布防**：IMU 低功耗中断监听，MCU 深度睡眠，4G 周期性心跳（如 30 min）。
- **S2 疑似**：唤醒 MCU，本地短提示音，开始积分计数，不上报（省电、防误扰）。
- **S3 确认威胁**：强警报（110 dB 脉冲）+ 上报 + 追踪 + 打开语音通道。
- **S5 撤回**：用户确认误报后，本次事件标记为负样本，用于后续阈值调优。

> 判定不要写死成单一阈值，建议做成**"时间窗内的加权投票"**：冲击能量、持续时长、车轮转动、位移、地理围栏、授权手机在场，各给一个权重与置信度，超过阈值才升级。阈值云端可下发，便于 OTA 调参。

### FR-3 现场威慑

| ID | 需求 | 优先级 | 验收标准 |
| --- | --- | --- | --- |
| FR-3.1 | 高分贝警报（脉冲/变频，避免听觉疲劳） | P0 | 距设备 10 cm ≥ 105 dB(A)，1 m ≥ 85 dB(A) |
| FR-3.2 | 警报可由 App 远程停止 | P0 | 停止指令 ≤ 3 s 生效 |
| FR-3.3 | 警报音可配置（警笛/语音/自定义） | P1 | 至少 3 种音效 |
| FR-3.4 | 本地预置语音威慑（"车辆已被监控，请立即离开"等） | P1 | 断网可播 |
| FR-3.5 | 灯光提示（夜间寻车/威慑） | P2 | 高亮 LED，可远程点亮 |

### FR-4 远程通知与语音干预

| ID | 需求 | 优先级 | 验收标准 |
| --- | --- | --- | --- |
| FR-4.1 | 告警推送至手机（系统通知 + App 内） | P0 | 触发到送达 P95 ≤ 10 s（信号良好） |
| FR-4.2 | 推送内容含：事件类型、时间、位置、当前状态 | P0 | 点击直达地图页 |
| FR-4.3 | 电话/短信兜底（推送未达或未响应时） | P1 | 分级升级：推送 → 短信 → 电话 |
| FR-4.4 | 一键远程语音喊话（App 按住说话 → 设备外放） | P0 | 建立连接 ≤ 2 s，端到端延迟 ≤ 500 ms |
| FR-4.5 | 设备端拾音回传（听现场） | P2 | 与 FR-4.4 共用音频链路 |
| FR-4.6 | 语音内容可自定义 / TTS 播报 | P2 | 文本下发 → 设备播报 |
| FR-4.7 | 告警关闭后的"事件回放"（时间线 + 位置轨迹） | P1 | 保留 ≥ 30 天 |

### FR-5 定位与追踪

| ID | 需求 | 优先级 | 验收标准 |
| --- | --- | --- | --- |
| FR-5.1 | GNSS 定位（GPS+北斗），App 地图展示 | P0 | 开阔环境 CEP50 ≤ 10 m |
| FR-5.2 | 按需定位（用户查询时唤醒） | P0 | 查询到返回 ≤ 15 s（热启动） |
| FR-5.3 | 追踪模式：持续上报并更新轨迹 | P0 | 上报间隔可配（5/10/30 s），可持续 ≥ 2 h |
| FR-5.4 | 基站/WiFi 辅助定位（室内、车库） | P1 | 无 GNSS 时给出 ≤ 500 m 量级位置 |
| FR-5.5 | 位置历史与轨迹回放 | P1 | 支持 7/30 天 |
| FR-5.6 | 寻车模式：近场 BLE 测距 + 声光提示 | P1 | 10 m 内可引导至设备 |
| FR-5.7 | 最后已知位置缓存（断网时） | P0 | 恢复联网后补传 |

### FR-6 设备防护与防拆

| ID | 需求 | 优先级 | 验收标准 |
| --- | --- | --- | --- |
| FR-6.1 | 开盖检测（微动/霍尔） | P0 | 开盖即告警，用备用电源发出 |
| FR-6.2 | 后备电源：主电池断开后维持告警与上报 | P1 | ≥ 30 s 告警 + 1 次上报 |
| FR-6.3 | 掉电/重启事件日志 | P1 | 记录时间戳与原因，联网后上报 |

## 7. 关键设计权衡

这一节是需求分析的"结论区"——把需求翻译成必须提前拍板的技术决策。

### 7.1 误报 vs 漏报：必须用产品手段，而不是算法手段解决

纯算法调参永远在"太灵敏"和"太迟钝"之间摇摆。真正的解法是**降低"必须报警"的定义难度**：

1. **分级响应**（S2 疑似只响短提示，不推送）——把大量噪声挡在推送之前。
2. **授权手机在场即撤防**——消灭最大的误报源（用户自己）。
3. **地理围栏 + 宽限期**——消灭第二大的误报源（家门口/公司停车区的日常碰撞）。
4. **用户负反馈闭环**——"这是误报"一键标记，云端聚合调参。
5. **默认灵敏度偏保守**——宁可少报，不可烦人；高危事件（位移、车轮转动）用另一套更激进的阈值。

> 建议把"误报率"写进 PRD 的验收门槛，并在小批量试用阶段用真实数据校准，而不是靠拍脑袋定阈值。

### 7.2 功耗预算（关键约束，建议尽早实测）

粗算（3.7 V 锂电，单节 3400 mAh ≈ 12.6 Wh）：

| 工作模式 | 平均电流（估算） | 续航（3400 mAh） | 备注 |
| --- | --- | --- | --- |
| 深度睡眠 + 心跳（30 min） | 0.2–0.5 mA | 60–90 天 | 依赖 4G PSM/eDRX |
| 布防（IMU 中断常开） | 0.5–1 mA | 45–60 天 | 与 FR-7.1 匹配 |
| 疑似唤醒（每小时数次） | 1–3 mA | — | 短时脉冲，影响小 |
| 追踪模式（GPS + 10 s 上报） | 60–120 mA | 24–48 h | 见 FR-7.2 |
| 警报（喇叭 + 4G） | 峰值 1.5–2 A | — | 需电容缓冲，防电压跌落重启 |
| 码表模式（V2） | 50–90 mA | 30–50 h | 需更大电池 |

结论与建议：

- **喇叭是峰值功耗的元凶**，必须在电源路径上加超级电容/大容量钽电容，否则一响就欠压重启。
- **GNSS 常开不可接受**，必须"按需 + 热启动 + 运动触发"。
- 电池选型建议 **2×18650 或等效软包（≥ 5000 mAh）**，为 V2 留余量；同时注意车架内高温对锂电寿命的影响。

### 7.3 通信制式选型

| 方案 | 覆盖/成本 | 功耗 | 语音能力 | 结论 |
| --- | --- | --- | --- | --- |
| 4G Cat.1 bis | 覆盖好，模组 ¥25–40 | 中（PSM 可接受） | 支持音频/VoLTE（视模组） | ✅ **推荐主选** |
| LTE-M / NB-IoT | 覆盖依赖运营商，NB 省电 | 极低 | 基本不支持实时语音 | 备选（低成本型号） |
| 2G | 退网中 | 低 | 支持 | ❌ 不建议 |
| LoRa/私有 | 需自建网关 | 低 | 无 | ❌ 不适合消费级 |
| 纯 BLE + 手机 | 零流量成本 | 极低 | 无 | 仅作辅助/近场 |

> Cat.1 是当前"覆盖 + 功耗 + 语音可能性 + 成本"的最优平衡点。国内模组供应链成熟（移远、合宙、广和通等），选型时优先确认三点：**是否内置 GNSS、是否支持 VoLTE/音频、PSM 电流实测值**。

### 7.4 "手机语音警告"的三种实现（成本差异巨大）

用户表述"手机可以通过语音方式警告"存在三种解读，务必确认：

| 方案 | 链路 | 研发量 | 成本 | 体验 | 建议 |
| --- | --- | --- | --- | --- | --- |
| **A. 预置语音/警笛 + App 触发播放** | MQTT 下发指令 → 设备播本地音频文件 | 低 | 低 | 威慑够用，但不能"说话" | ✅ **V1 采用** |
| **B. VoLTE 电话** | App 直接拨打设备 SIM → 设备自动接听外放 | 中 | 通话费；**物联网卡多禁语音** | 最自然，延迟低 | ⚠️ 需先验证语音卡可行性，V1.5 评估 |
| **C. 实时音频流（WebRTC/自研 UDP）** | App ↔ 云 ↔ 设备 双向音频 | 高 | 服务器带宽 + 流量 | 最好（可对讲、可听现场） | 放 V2 |

> 关键提醒：**国内物联网卡普遍关闭语音功能**，方案 B 需要普通 SIM 或专门的语音卡，会影响商业模型（谁付话费、号码谁来管）。方案 C 则需要设备端具备音频编解码与持续上行带宽，功耗与流量成本都要重估。**建议 V1 用 A 验证"远程威慑"是否真的有效，再决定是否投入 B/C。**

### 7.5 定位在真实环境中的失效点

- **金属车架遮挡**：GNSS 天线必须朝上、远离管壁，优选陶瓷贴片 + 壳体顶部开窗，或 FPC 天线贴壳。
- **地下车库/楼道**：GNSS 基本失效。必须依赖**基站/WiFi 辅助定位 + 最后已知位置 + BLE 寻车**三件套。
- **城市峡谷**：多径严重，建议开启多星座（GPS+北斗+GLONASS）+ SBAS，并做轨迹平滑。
- **室内定位体验**：不要承诺"精确到米"，要承诺"能带你到楼下/单元门口，最后靠声光找到"。

### 7.6 防拆的对抗性设计

这是防盗产品最容易被低估的部分。盗贼的第一反应往往是"先拆掉那个盒子"。

- **物理层**：异形螺丝、灌封、外壳无外露螺丝、扎带内藏、安装位置选车架下管内侧/座管后方（不显眼）。
- **电气层**：开盖微动开关 + 霍尔 + 断线检测 + 后备小电池（拆机时仍能发一次告警）。
- **逻辑层**：**静默上报**——检测到可疑时先不打草惊蛇（不响、不亮），把位置与轨迹悄悄传上去，等用户确认后再远程触发警报。这比"一碰就吼"更能抓到人。
- **信息层**：设备外观不要让人一眼看出是追踪器（伪装成尾灯/码表底座/水壶架附件是常见思路）。

### 7.7 外壳：3D 打印是"原型与定制"手段，不是量产的终点

| 阶段 | 工艺 | 理由 |
| --- | --- | --- |
| 原型 | FDM/SLA 3D 打印 | 快速迭代、贴合验证 |
| 小批量 | SLA/尼龙 SLS + 后处理 | 强度与耐候可接受，单价高（¥30–80） |
| 量产 | 注塑（PC/ABS 或 PA+GF）+ 硅胶包覆 | 单件成本可降到 ¥5–10，一致性好 |
| 个性化 | 3D 打印适配件（不同管径/管型） | SKU 爆炸的解法：**通用主体 + 可换适配件** |

> 强烈建议采用"**通用主机 + 参数化适配件**"的结构：主机一套模具走量，适配件用 3D 打印覆盖长尾车型。这样既保留了"贴合车架"的卖点，又不会让模具费和库存拖死项目。
>
> 另外三个容易被忽略的工程点：**散热**（4G 模组 + 充电发热在密闭壳体内积聚）、**密封**（O 型圈 + 灌胶，充电口是最大漏点）、**减震**（车架高频振动会加速焊点疲劳，需硅胶垫 + 灌封）。

### 7.8 为第二曲线预留（避免推倒重来）

V1 硬件选型时，按 V2 的最坏负载倒推：

| 项 | V1 够用 | 为 V2 预留 | 建议 |
| --- | --- | --- | --- |
| MCU | Cortex-M0+ | M4F/M33，≥ 512 KB Flash | 选 M33，留算力做滤波/压缩 |
| GNSS | 单星座低速 | 多星座、≥ 1 Hz、低功耗热启动 | 选支持 1 Hz 连续输出的模组 |
| 电池 | 3400 mAh | ≥ 5000 mAh | 直接上大容量，摊薄在整机成本里很小 |
| BLE | 仅配网 | 同时做中心+外设（连心率/踏频） | 选支持多连接的 BLE 5.x |
| 存储 | 无 | ≥ 8 MB Flash 缓存轨迹（断网续传） | 加 SPI Flash |
| 扩展 | 无 | 预留 I2C/UART 排针或弹片 | 壳体留调试口（灌封前） |

> 一句话：**V1 省下的每一块钱，都可能在 V2 变成一次硬件返工。** 在 MCU、电池、存储这三项上多花 ¥10，比 V2 重新开模划算得多。

### 7.9 合规与认证（时间风险，必须在硬件定稿前启动）

| 事项 | 说明 | 建议动作 |
| --- | --- | --- |
| 无线电型号核准（SRRC） | 带 4G/WiFi/BLE 发射的整机需要核准 | 优先选已过 SRRC 的模组，整机仍走流程；预留 2–3 个月 |
| 电信设备进网许可 | 蜂窝终端进网要求 | 使用已进网模组可简化，与模组厂确认授权方式 |
| CCC 认证 | 视产品类别（电源/信息技术设备） | 咨询认证机构确认是否适用 |
| 电池安全与运输 | GB 31241（锂电安全）、UN38.3（运输） | 选带认证的电芯与 Pack 厂，别省这一步 |
| 环保 | RoHS / REACH | 供应链声明与物料清单核查 |
| 地图与定位服务 | 地图展示需使用有资质的地图服务商 | 用高德/腾讯/百度等 SDK，不自行绘制公开地图 |
| 个人信息保护 | 位置信息属敏感个人信息：单独同意、最小必要、可删除、加密存储 | 隐私政策与后端权限设计要在 Phase 1 前置 |
| 录音边界 | 公开场合的音频采集法律边界敏感 | V1 不做持续录音；事件触发短音频需明确告知且默认关闭 |

> 认证是"**时间风险**"而非纯技术风险：天线布局、发射功率、杂散指标一旦在硬件定稿后才暴露问题，改板重测会直接拖掉上市窗口。**把合规排期当成研发关键路径的一部分。**

## 8. 竞品与差异化

### 8.1 四类替代方案

| 类别 | 代表形态 | 优势 | 短板 |
| --- | --- | --- | --- |
| 蓝牙防丢器 | AirTag / Tile 类 | 便宜、免充电、室内定位好 | 无 GPS、无警报、依赖人群网络、无法远程干预 |
| GPS 追踪器 | 车载定位器类 | 有定位、有轨迹 | 多数需订阅、体积大、显眼、无本地威慑、防盗判定弱 |
| 智能锁 | 电子锁/报警锁 | 锁车即报警、有品牌信任 | 只在锁附近有效，车被搬走即失效 |
| 整车内置防盗 | 高端电助力/城市车 | 集成度最高、体验最好 | 绑定整车、价格高、无法后装、维修难 |

### 8.2 差异化定位

1. **闭环而不是监控**：感知 → 判定 → 本地威慑 → 远程干预 → 寻回引导，一条链打通。多数竞品只做到"监控 + 通知"。
2. **对抗性设计**：把"失联""被拆""被屏蔽"当成一等告警，而不是等设备还活着才工作。
3. **隐蔽 + 贴合**：车架一体化外观，不是绑在座管上的黑盒子。
4. **可迁移 + 可升级**：换车能拆走，未来能当码表——**一机多用摊薄用户的心理成本**。
5. **中国本地化**：北斗、国内推送通道、本地地图与合规，是海外产品难补的短板。

### 8.3 定价与商业模式（待定，但需尽早想）

| 模式 | 优点 | 风险 |
| --- | --- | --- |
| 纯硬件一次性 | 决策简单、易传播 | 云与流量成本无法持续，告警服务难长期免费 |
| 硬件 + 订阅（流量/云/高级告警） | 可持续、LTV 高 | 用户抵触，需明确"免费版够用"的边界 |
| 硬件 + 保险/防盗服务分成 | 差异化强 | 需合作方，周期长 |

> 建议：**基础防盗功能永久免费（含首年流量），高级功能（实时追踪时长、轨迹云存储、家庭成员、语音包）订阅**。这样既不破坏"买了就能用"的信任，又留出收入曲线。

## 9. MVP 范围与路线图

### Phase 0：可行性验证（2–4 周，桌面/原型）

**目标**：证明"能判得准、能喊得响、能找得到"。

- 用开发板 + 现成 4G/GNSS 模组搭台架，验证：IMU 特征能否区分"碰倒 / 撬锁 / 推行 / 抬走"。
- 验证喇叭声压与峰值功耗对电源的冲击。
- 验证车架金属对 GNSS 的实际影响（装车实测，而非桌上测）。
- 验证 MQTT 告警链路端到端时延。

**退出条件**：四类动作的识别准确率 ≥ 90%，误报率可控；告警端到端 ≤ 10 s。

### Phase 1：防盗 MVP（8–12 周）

- FR-1（布防/撤防/自动）、FR-2.1–2.4、FR-3.1–3.2、FR-4.1–4.4、FR-4.7、FR-5.1–5.3、FR-5.7、FR-6.1/6.5/6.6、FR-7.1–7.5、FR-8.1–8.4、FR-9.1–9.4、FR-9.8、FR-10.1–10.4。
- 外壳：1–2 种主流管径，3D 打印小批量。
- 语音：方案 A（预置语音 + App 触发）。
- **不做**：屏幕、ANT+、双向对讲、多车型 SKU、B 端后台。

**退出条件**：10–20 台真实用户内测 4 周，误报率 ≤ 0.5 次/周，无致命故障。

### Phase 2：产品化（12–16 周）

- 注塑外壳 + 参数化适配件；IP67 与高低温认证；SRRC/进网许可。
- FR-1.4/1.5/1.6、FR-4.3/4.5、FR-5.4–5.6、FR-6.2–6.4、FR-9.5–9.7、FR-10.5–10.7。
- 语音方案 B/C 选型与验证；寻车体验打磨；订阅体系上线。

### Phase 3：第二曲线（按需）

- FR-11 全量；可与码表厂商/骑行社区合作导流。
- 关键前提：V1 硬件已按 §7.8 预留，否则先评估是否推出"Pro"版本。

## 12. 需求优先级汇总（MoSCoW）

**Must（MVP 必须）**
布防/撤防与自动布防 · IMU+霍尔+位移的多传感器判定 · 分级状态机 · 本地 105 dB 警报 · 推送 ≤ 10 s · 一键语音喊话（方案 A） · GNSS 定位与查询 · 追踪模式 · 防拆开关 · IP67 贴合外壳 · 45 天续航 · 磁吸充电 · 设备绑定与 OTA。

**Should（首个量产版）**
地理围栏 · 手机在场自动撤防 · 多车/共享 · 基站辅助定位 · 寻车模式（BLE+声光） · 后备电源 · 告警升级（短信/电话） · 事件回放 · 差分 OTA · 运营后台。

**Could（后续）**
双向对讲 · 设备拾音 · TTS 自定义语音 · 气压计场景判断 · 灯光 · 声音事件识别 · B 端 API · 保险合作。

**Won't（V1 明确不做）**
屏幕与导航 · ANT+ 传感器接入 · 骑行数据可视化 · 多车型全 SKU · 自研地图 · AI 行为识别。

### 13.1 传感器清单（建议）

| --- | --- | --- | --- |

### 13.2 术语

- **PSM/eDRX**：蜂窝网络的省电模式/扩展非连续接收，决定待机功耗。
- **CEP50**：圆概率误差，50% 的定位结果落在该半径内。
- **静默上报**：检测到可疑时不触发现场警报，仅后台记录与上报告警。
- **参数化适配件**：用同一套参数化模型生成不同管径/管型的外壳配件。

### 13.3 假设与待验证项

- 续航数据为纸面估算，需 Phase 0 实测校准。
- 成本估算基于 1k 量级、国内供应链，未含模具与认证摊销。
- 语音方案 B 的可行性取决于运营商对物联网卡语音能力的政策，需实际验证。
- 合规要求为一般性提示，具体认证路径需咨询专业机构。
