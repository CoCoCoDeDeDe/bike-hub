## 1. 原型要证明什么

概念原型不是"把功能全做一遍"，而是回答四个问题。任何工作只要不能回答这四个之一，就不该排进前 8 周。

| # | 待验证问题 | 验证方式 | 判据 |
| --- | --- | --- | --- |
| V1 | 传感器能不能区分"碰一下"和"在撬锁/在抬车" | 四类动作各录 20 次，离线看特征分布 | 关键两类（撬/抬）与误报源可分，召回 ≥ 90% |
| V2 | 喇叭响的时候，系统会不会被自己打崩 | 同时开喇叭 + 4G 上行，看电压跌落 | RB 复位，4G 不掉线 |
| V3 | 装到车上以后，GPS 还能不能定位 | 开阔/楼下/车棚/地库各测 5 min | 开阔 TTFF < 60 s，CEP ≤ 20 m |
| V4 | 从"车动"到"手机响"要多久 | 打时间戳，端到端测 20 次 | P95 ≤ 10 s |

> **V1 是最难、也最值钱的一个。** 它决定了这个产品到底是"玩具"还是"真的有用"。建议把前两周时间全部投入到这里，不要急着写 App。

## 2. 总体方案

```
┌─────────────────────────── 自行车上 ────────────────────────────┐
│                                                                  │
│  IMU(LIS3DH) ───────────I2C──┐                                 │
│  霍尔(车轮/开盖) ──────GPIO──┤                                 │
│  光感(可选) ───────────ADC───┤                                 │
│                               ▼                                 │
│                        ESP32-S3 (主控)                          │
│                     ┌────────┴────────┐                        │
│                  UART│                 │I2S                    │
│                     ▼                 ▼                        │
│          4G+GNSS 模组(Air780EG)   MAX98357A + 喇叭              │
│                     │                                          │
└─────────────────────┼──────────────────────────────────────────┘
                      │ MQTT over 4G
                      ▼
              ┌───────────────┐        ┌──────────────────┐
              │  MQTT Broker  │◄──────►│ Node-RED 控制台  │
              │ (mosquitto)   │        │ 看位置/选语音/收告警│
              └───────────────┘        └────────┬─────────┘
                                                │
                                         手机浏览器 / 通知
```

**设计原则**：

1. **主控 + 通信模组分离**。ESP32 负责感知、判定、音频、配网；4G 模组只当"猫"用 AT 指令驱动。职责清晰、故障可定位。
2. **云端不写代码**。用 MQTT Broker + Node-RED 拼出控制台，省掉 App 与服务端开发，把时间留给判定算法。
3. **先通链路再优化功耗**。原型阶段用大电池 + 频繁唤醒，别在第一周纠结 µA 级电流。

## 3. 硬件选型与 BOM

### 3.1 主控：ESP32-S3 还是 C3 SuperMini

**结论：原型用 ESP32-S3-DevKitC-1（N16R8）；ESP32-C3 SuperMini 不推荐，卡点不是性能而是引脚。**

| 项 | ESP32-S3-DevKitC-1 | ESP32-C3 SuperMini |
| --- | --- | --- |
| 内核 | 双核 LX7 @240 MHz | 单核 RISC-V @160 MHz |
| 可用 GPIO | ~44（2×22 排针） | **~13**（且含 UART0 调试口） |
| I2S / UART | 2 / 3 | 1 / 2 |
| RAM / PSRAM / Flash | 512 KB / **8 MB** / 16 MB | 400 KB / 无 / 4 MB |
| 尺寸 | 25.4 × 63 mm | **22 × 18 mm** |
| 深睡电流 | ~7 µA | ~5 µA |
| 价格 | ¥40–60 | **¥15–25** |
| 调试 | 原生 USB + 串口，可同时用 | USB Serial/JTAG |

性能上 C3 其实够：播放 WAV 不需要解码，4G 用模组内置 MQTT 时主控负载很轻。**真正的问题是引脚不够。**

引脚预算（完整形态）：

| 用途 | 引脚 | 备注 |
| --- | --- | --- |
| IMU I2C（SDA/SCL） | 2 | 可与光感共用 |
| IMU INT1 | 1 | 硬件唤醒，必须有 |
| 4G UART（TX/RX） | 2 | 3.3 V TTL，直连，见 §3.2 |
| 4G PWR_EN | 1 | 电源使能，可省 |
| GPS UART（TX/RX） | 2 | 独立 NMEA 串口，也可以与 AT 挤一路 |
| I2S（BCLK/LRC/DIN） | 3 | 音频输出 |
| 功放使能（SD） | 1 | 软启停防爆音 |
| 霍尔-车轮 | 1 | |
| 霍尔-开盖 | 1 | |
| 电池 ADC | 1 | |
| 按键 / LED | 2 | 可用板载 |
| **合计** | **17–19** | |

C3 SuperMini 引出 13 个，其中 2 个是 UART0 调试口。硬塞也能塞下（砍掉开盖霍尔、PWRKEY 用 RC、LED 用板载），但：

- **零余量**：加个 SD 卡、加个屏幕、加个 BLE 传感器就没位置了。
- **调试难受**：接满外设后没有空闲引脚抓波形、加逻辑分析仪。
- **Flash 只有 4 MB**：8 段 WAV 就占一半，轨迹缓存没地方放。

三档选择：

| 目标 | 选型 |
| --- | --- |
| ✅ **原型 + 完整功能** | ESP32-S3-DevKitC-1 N16R8（¥40–60），引脚和 PSRAM 都从容 |
| 只做"震动 + 定位 + 4G"，不要音频 | ESP32-C3 SuperMini 可行，但要砍外设 |
| 最终小体积成品 | 自己画板用 ESP32-S3-WROOM-1-N8R2（18 × 25.5 mm，引脚够，¥20） |

> 一句话：**C3 是"能做"，S3 是"做得舒服"。** 这个项目要验证判定算法，调试余量比 20 块钱和 45 mm 长度重要得多。外壳做到 130 mm 长完全放得下 S3。

### 3.2 通信：Air780EG 核心板（已确认型号）

**已确认型号**：`DTU_780EG-V1.00`，合宙 Air780EG，32 × 49 mm。这块板把裸模组该操心的都做完了，是当前方案的最优解。

| 参数 | 实际值 | 对本项目的影响 |
| --- | --- | --- |
| 供电 | **5–12 V** | ⚠️ 18650 必须升压到 5 V，多一块升压板 |
| 串口 | **3.3 V TTL**，可直接连 3.3 V/5 V 系统 | ✅ **省掉电平转换**，绕开最大的坑 |
| GNSS | 内置，另有独立数据串口 | ✅ 可与 AT 通道分离，解析干净 |
| SIM | Nano 自弹卡座 | ✅ 物联网卡正好 |
| 固件 | AT / IRTU / LuatOS 三选一 | ✅ **选 AT** |
| 4G 天线 | IPEX | 需确认代数（1 代 2 mm / 4 代 1.2 mm） |
| GPS 天线 | IPEX，**有源** | 必须买有源天线 |
| USB | 仅烧录/看日志，**不能供电** | 调试时要另找 5 V 供电 |

**接口定义**：

| 引脚 | 用途 | 接 ESP32 |
| --- | --- | --- |
| VCC | 5–12 V 输入 | ← 升压模块 5 V |
| GND | 地 | 共地（必须） |
| TXD1 / RXD1 | AT 指令通道 | UART1 |
| PWR_EN | 电源使能 | 接 GPIO，或直接拉高常开 |
| GPS_TX / GPS_RX | GNSS 独立串口 | UART2 |
| DTR | 烧录复位 | 原型可不接 |

**串口怎么用：两路，别挤一路**

厂商说"一个主串口就能通信并获取 GPS 数据"，确实可以——但 NMEA 和 AT 响应会混在一条流里，解析逻辑会变得很难看。ESP32-S3 有 3 个 UART，直接用两路：

```
UART1 ← TXD1/RXD1  → 纯 AT 指令（注网、TCP、发数据）
UART2 ← GPS_TX/RX  → 纯 NMEA（TinyGPSPlus 直接解析）
```

代价是 2 个 GPIO，换来的是"GNSS 挂了不影响联网、AT 超时不吞掉定位数据"。

**固件选 AT，别选 LuatOS**

三种固件里：

| 固件 | 适合谁 | 结论 |
| --- | --- | --- |
| **AT** | 外挂 MCU 做主控 | ✅ 你的情况。ESP32 当大脑，模组只当网卡 |
| IRTU | 无 MCU、纯透传 | 用不上，会失去控制权 |
| LuatOS | 单模组独立开发 | ✗ 和 ESP32 抢主控角色 |

**网络层建议**：用 `AT+CIPSTART` + `AT+CIPSEND` 做 TCP 透传，**MQTT 协议栈跑在 ESP32 上**（PubSubClient）。不用模组自带的 MQTT AT 指令，理由：ESP32 端能抓包、能重连、能打日志，出问题好排查。

**供电：必须升压，且只升两路**

板子要 5 V 起，18650 是 3.7 V，所以：

```
18650 ×2（并联 6800 mAh）
   ├─► TPS61088 同步升压 5 V ──► Air780EG VCC + ESP32 VIN
   │      └─► 1000 µF/16 V（升压输入 1 + 输出 1）
   ├─► 直供 ──► 喇叭（MAX98357A）/ 锁电机 / 霍尔 / IMU
   └─► 1000 µF/16 V ×2（每路功放电源脚就近）
```

**定选 TPS61088，不选 MT3608**：MT3608 输入侧限流 2 A，而 4G 发射峰值 2 A@3.8 V ≈ 7.6 W，一发射就掉压发热，故障表现是"数据发到一半重启"——最难定位的一类。TPS61088 同步升压，10 A 能力，¥8 差价买确定性。

**只给 Air780EG 和 ESP32 升压**：功放、电机、传感器全都吃 3.7 V 直供，少一级转换就少一路干扰源和一份损耗。全局升压是把 6.8 Ah 的电池白白烧在转换效率上。

4G 模组峰值 2 A，升压模块的输入侧瞬时也要 3 A 左右，18650 完全扛得住，但**走线要粗**（别用细杜邦线过 2 A）。

**电容选型：容量够、耐压对、耐温 105 °C**

全部电解统一成 **1000 µF / 16 V / 105 °C / ⌀8×16（或 ⌀10×12.5）** 一种规格，按 20 个/包买一包。不要买 50 V / 2200 µF / ⌀16×31 mm 的通用品——耐压是 5 V 轨的 10 倍，体积大 3 倍，压降反而更大。通用 105 °C 品的 2 A 突发压降约 220 mV（5 V 轨到 4.78 V），已经完全够用，不必刻意追低 ESR。详见 [BOM 的电容说明](bom.md#b1-通信)。

**调试时的供电**：板子 USB 不能供电，所以准备一个 5 V/2 A 电源适配器 + 杜邦线，或者用 XH2.54 转 USB 供电线，插上就能单独玩模组。

### 3.3 传感器：LIS3DH 够用，而且是个好选择

**结论：LIS3DH 完全可以作为主传感器，不必上 6 轴。**

| 参数 | LIS3DH | 对本项目的意义 |
| --- | --- | --- |
| 轴数 | 3 轴加速度 | 震动、冲击、倾角都能测 |
| 量程 | ±2/4/8/16 g | **选 ±4 g**，撬锁冲击容易超 2 g 饱和 |
| 分辨率 | 10 位 | ±4 g 时约 7.8 mg/LSB，足够 |
| ODR | 1 Hz–5.3 kHz | 50 Hz 采日常，高速档可做撬锁频谱 |
| FIFO | 32 级 | 50 Hz 下约 0.64 s，配合水位中断批量读，减少唤醒 |
| 中断 | INT1/INT2，可配阈值/持续时间 | **硬件唤醒的关键**，MCU 可以一直睡 |
| 硬件功能 | 6D 方向、AOI、自由落体、click | 省软件算力，也省误报 |
| 功耗 | 低功耗 10 Hz 约 2 µA | 常开监测不心疼 |
| 价格 / 生态 | ¥5–8，Adafruit 库成熟 | 资料多，少踩坑 |

**LIS3DH 的几个硬件特性正好对上需求**：

- **6D 方向中断**：车从直立变倒伏，硬件直接给中断，不用软件算姿态。比阈值判断可靠。
- **AOI（And/Or 组合中断）**：比如"加速度 > 1.5 g **且** 持续时间 > 200 ms"才触发，一次配置就把单次轻碰过滤掉。
- **FIFO 水位中断**：攒够 16 个点再唤醒 MCU，50 Hz 下唤醒频率从 50 次/秒降到 3 次/秒。
- **click 中断**：可以识别"敲击"，用于调试和标定，很有意思。

**它缺什么**：没有陀螺仪。所以：

| 场景 | 3 轴够不够 |
| --- | --- |
| 判断"车被抬起"（垂直加速度突变 + 姿态变化） | ✅ 够，jerk 特征很明显 |
| 判断"车倒下" | ✅ 够，6D 中断直接给 |
| 判断"被推行" | ✅ 靠霍尔，不靠 IMU |
| 判断"摔车"（未来码表） | ⚠️ 需要陀螺仪 |
| 骑行姿态/坡度平滑（未来） | ⚠️ 陀螺仪更稳 |

**如果你希望一步到位兼顾未来码表**，可以直接上 **LSM6DSO**（6 轴，低功耗 + FIFO + 有限状态机，¥15–20），Arduino 生态也不错。但注意：**多花的钱和复杂度，在原型阶段换不来判定精度**——因为判定主要靠加速度特征和车轮信号。

其余传感器：

| 器件 | 用途 | 价格 | 备注 |
| --- | --- | --- | --- |
| **LIS3DH** | 震动/冲击/倾角/落下 | ¥5–8 | ✅ 主传感器，选 ±4 g |
| 霍尔开关（低功耗，如 AH1815） | 车轮转动 / 开盖 | ¥1–3 | 车轮用高灵敏度，开盖用普通 |
| NTC 10K | 电池温度 | ¥1 | 别省 |
| 光敏电阻 | 开盖辅助 | ¥1 | 可选，I2C 光感更好但占地址 |

> 采购提示：LIS3DH 常以"GY-61 / ADXL345 替代"名义卖，注意看清楚型号。**LIS3DH 的 I2C 地址是 0x18（SA0 接地）或 0x19（接 VCC）**，接错会扫不到。

### 3.4 音频

| 器件 | 用途 | 价格 |
| --- | --- | --- |
| MAX98357A 模块（I2S，**SD/GAIN 引出**） | 推喇叭 | ¥6–10 |
| 4 Ω 3 W 带腔体喇叭，**灵敏度 ≥ 90 dB/W/m** | 发声 | ¥8–15 |
| 1000 µF / 16 V **105 °C** 电解 ×2 | 吸收喇叭峰值电流 | ¥2 |

**认准 A 不是 B**：MAX98357A 是标准 I2S，MAX98357B 是为左对齐（Left-Justified）优化的。ESP32 的 I2S 外设默认输出标准 I2S，B 用不上。

**3.2 W 是 5 V 的数据**。本项目功放直供 3.7 V，4 Ω 实际只有约 **1.5 W**：

| 供电 | 4 Ω 实际 | 90 dB 喇叭 | 92 dB 喇叭 | 95 dB 喇叭 |
| --- | --- | --- | --- | --- |
| **3.7 V** | 1.54 W | 91.9 dB | **93.9 dB** | 96.9 dB |
| 5 V | 2.81 W | 94.5 dB | 96.5 dB | 99.5 dB |

自行车铃约 90–100 dB。**与其为 2.6 dB 改接 5 V（升压要扛 2 A 瞬态），不如挑灵敏度 92 dB 以上的喇叭**——同样 1.5 W 白得 2 dB，不动电路。

喇叭一定要**带腔体**（不是裸喇叭），声压能高 5–10 dB。外壳上开导音孔，孔内侧贴防尘网。

## 4. 电源设计（三个必须避开的坑）

### 坑 1：喇叭一响，系统重启

D 类功放瞬时电流可达 1.5–2 A。如果电池内阻大、走线细、没有储能电容，电压瞬间跌到 3.0 V 以下，ESP32 直接 brownout 复位——你会看到"警报响了一声就死机"。

**对策**：

- 功放电源脚就近并 **1000 µF（105 °C）+ 100 nF 陶瓷**。
- 电源走线加粗（≥ 1 mm），电池到板子用硅胶线。
- 软件上：响之前先把 4G 上行暂停，响完再恢复（错峰用电）。

### 坑 2：4G 模组把电池吃空

Cat.1 模组在搜网/发射瞬间能到 2 A，平均也有几十 mA。**不要让它常驻联网**，用 PSM/定时心跳：

```
每 10 min 唤醒 → 连网 → 上报状态 → 断开/进 PSM → 睡
事件触发时 → 立即唤醒 → 保持连接 → 追踪模式
```

### 坑 3：充电时设备还在工作

边充边用会让电量计不准、温度升高。原型阶段可以接受，量产要处理（充电时暂停告警或改为"充电模式"）。

**原型阶段的现实目标**：待机 2–4 周即可，不要追 45 天。等判定逻辑稳定了再谈省电。

## 5. 语音方案：预制录音 + 手机选播

按你的定位（预置录音、手机手动选择），链路极简，**不需要麦克风、不需要实时音频、不需要 TTS**。

```
手机(Node-RED 面板) ──MQTT cmd: play/3──► 设备
设备: 查本地音频清单 → I2S 播放 /audio/3.wav → 回 ack
```

### 5.1 音频格式的选择

| 格式 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| **WAV / PCM 16 bit 16 kHz 单声道** | 零解码、零依赖、绝对可靠 | 文件大（16 kHz×2 B = 32 KB/s） | ✅ **推荐**，8 s 录音约 256 KB |
| MP3 | 省空间 | 需要解码库（ESP8266Audio/libmad），占 CPU 与内存 | 后期再说 |
| IMA-ADPCM | 压缩 4:1，解码极简 | 需要自己写解码，音质一般 | 进阶选项 |

对比一下：ESP32-S3 的 Flash 有 8–16 MB，存 8 段 8 秒 WAV 才 2 MB。**为省这点空间引入解码器不值得。**

### 5.2 音频怎么进设备

| 方式 | 适用阶段 | 说明 |
| --- | --- | --- |
| 烧录进 LittleFS 分区 | ✅ **原型阶段** | 用 `pio run -t uploadfs` 一次性写入，改音频就重烧 |
| 通过 WiFi 网页上传 | 后期 | ESP32 起一个小 HTTP 服务，浏览器拖文件进去 |
| 通过 4G 下载 | 后期 | OTA 方式下发，需要断点续传与校验 |

> 原型阶段用第一种就好。做一段 `audio/index.json` 描述清单（id、名称、时长、音量），设备上电上报给云端，手机面板据此生成下拉框。

```json
[
  {"id": 1, "name": "警笛-标准",   "file": "/a1.wav", "vol": 90, "loop": true},
  {"id": 2, "name": "警笛-急促",   "file": "/a2.wav", "vol": 95, "loop": true},
  {"id": 3, "name": "语音-已报警", "file": "/a3.wav", "vol": 85, "loop": false},
  {"id": 4, "name": "语音-请离开", "file": "/a4.wav", "vol": 85, "loop": false}
]
```

### 5.3 播放控制的细节

- **防卡顿**：I2S 用 DMA 双缓冲，提前把文件读进 PSRAM（8 s 的 WAV 才 256 KB，S3 的 8 MB PSRAM 随便放）。
- **避免削顶**：MAX98357A 增益选 9 dB 起步，音量靠软件（PCM 缩放）调，不要靠功放增益硬拉。
- **循环警报**：用 `loop=true` 无缝循环，但设个上限（比如 3 分钟自动停），防止扰民和自己忘记关。
- **音量策略**：警报用大音量，语音威慑用中等音量（太大会破音、听不清词）。

### 5.4 手机端怎么"选"

原型阶段不要写 App。用 **Node-RED Dashboard 2.0** 做一个网页：

- 下拉框（从 `index.json` 生成）+ 播放按钮
- 音量滑块、循环开关
- 一个"停止"红按钮（这个必须有，别让自己关不掉）

手机浏览器打开即可，还能加到主屏幕当 PWA 用。

## 7. 判定算法原型

### 7.1 先采数据，再谈算法

**第一步不是写状态机，是写一个"录制模式"**：拨码开关或 MQTT 指令进入录制，50 Hz 采样 10 s，通过 WiFi 把 CSV 传到电脑。然后按动作分类采集：

| 类别 | 具体动作 | 次数 | 备注 |
| --- | --- | --- | --- |
| A 误报源 | 轻碰车身、靠车、放包、风吹、路人擦过 | 各 10 | **这是最重要的一类** |
| B 挪车 | 抬后轮挪、推车 | 各 10 | 用户自己挪车，不该报警 |
| C 撬锁 | 用螺丝刀/剪钳模拟剪锁、撬锁 | 各 10 | 真威胁 |
| D 抬走 | 整车抬起、装车 | 各 10 | 真威胁 |
| E 推行 | 撑起脚撑后转动车轮 | 10 | 车轮信号最可靠 |

每类 10–20 次，场地选**真实停车场景**（楼下、车棚），不要只在桌上测。

### 7.2 候选特征（先手工算，够用）

| 特征 | 计算 | 物理含义 |
| --- | --- | --- |
| `a_rms` | 1 s 窗内加速度模长的 RMS | 震动能量 |
| `a_peak` | 窗内峰值 | 冲击强度 |
| `jerk_max` | 加速度一阶差的峰值 | 突变程度（抬车最明显） |
| `tilt_delta` | 姿态角变化量 | 车被倾斜 |
| `zcr` | 窗内过零率 | 高频 vs 低频（撬 vs 推） |
| `dur` | 超阈值持续时间 | 持续撬 vs 单次碰 |
| `wheel` | 霍尔脉冲计数 | 车轮是否在转 |
| `disp` | GNSS 位移 | 是否被移动 |

### 7.3 状态机（原型版）

```
S0 SLEEP ──IMU 中断──► S1 VERIFY
S1 VERIFY: 积分窗口 2 s
    if a_peak < 1.2 g and dur < 0.3 s  → 回 S0（轻碰，忽略）
    if wheel > 0 or tilt_delta > 15°    → S3 ALARM（直接升级）
    if 持续冲击 dur > 2 s               → S3 ALARM
    if 2 s 内触发 3 次                  → S2 SUSPECT
    else                                → 回 S0

S2 SUSPECT: 本地短提示音（200 ms），不上报
    if 10 s 内升级条件成立 → S3
    if 10 s 无后续          → 记录负样本，回 S0

S3 ALARM: 喇叭（选默认音频）+ 上报 + 追踪 + 保持 60 s 冷却
```

### 7.4 影子模式（强烈建议）

**第一个月不要真报警。** 加一个"影子模式"开关：判定逻辑照跑、事件照上报，但喇叭不响、手机只收到"这类事件你会收到告警"的静默通知。

一周下来你会得到：

- 每天到底有几个"疑似事件"（真实误报率）
- 哪些场景是误报大户（邻居挪车？风？猫？）
- 阈值该往哪调

> 没有影子模式，你会在装车第二天因为半夜误报把设备拆了。**这是本项目最省钱的一个开关。**

### 7.5 阈值怎么定

不要拍脑袋写 `1.5 g`。流程是：

1. 采集 A–E 五类数据，存 CSV。
2. 写个 Python 脚本（30 行）算特征，画箱线图 / 散点。
3. 找能把 A 类（误报源）和 C/D 类分开的阈值。
4. 定完阈值做混淆矩阵，看召回与误报。
5. 装车跑一周影子模式，用真实数据复核。

如果规则分不开（很可能），再考虑：

- 加特征（频域能量、互相关）
- 上轻量分类器（决策树/随机森林导出成 C 数组，或 TFLite Micro 的 1D-CNN）
- 但**先试规则**，因为规则可解释、好调、省电。

## 8. 通信与云端（不写代码的玩法）

### 8.1 本地 MQTT Broker

你的环境是 WSL2，Docker 用不了，最省事的是：

```bash
sudo apt install mosquitto mosquitto-clients
# 测试
mosquitto_sub -t 'bikehub/#' -v
```

公网访问（设备在 4G 上，需要能连到你的 broker）：

- 方案 A：家里路由器做端口映射 + 公网 IP（有公网 IP 才行）
- 方案 B：用公共测试 broker（如 `broker.emqx.io`，**仅测试，数据公开**）
- 方案 C：买个 1 核 1 G 云主机（¥60/年学生机 / 轻量应用服务器）+ mosquitto

> 原型阶段建议 **B 做联调、C 做正式**。别在 4G NAT 穿透上耗时间。

### 8.2 Topic 设计

| Topic | 方向 | 载荷 |
| --- | --- | --- |
| `bikehub/{id}/state` | 上行 | 电量、温度、布防、信号、固件版本、音频清单 |
| `bikehub/{id}/evt` | 上行 | 事件：type、level、ts、特征值 |
| `bikehub/{id}/loc` | 上行 | lat、lon、acc、speed、ts |
| `bikehub/{id}/ack` | 上行 | 命令回执 |
| `bikehub/{id}/cmd` | 下行 | arm / disarm / play/{id} / stop / track/{sec} / reboot / shadow |

`{id}` 用 MAC 后 6 位或自定字符串即可。载荷用 JSON，别用二进制（原型阶段可读性 > 效率）。

### 8.3 Node-RED 控制台

```bash
npm install -g node-red
node-red   # http://localhost:1880
```

装 `node-red-dashboard` 与 `node-red-contrib-web-worldmap`，拖出：

- **状态卡片**：电量、在线、布防状态
- **地图**：worldmap 显示最后位置（OSM 底图）
- **语音选择**：下拉框（从 state 的音频清单生成）+ 播放/停止按钮
- **事件流**：表格显示最近事件
- **告警通知**：接 `telegram` / 邮件 / `bark` 节点

> 这样你**不用写一行 App 代码**，手机上浏览器打开就能用。等玩法验证了再考虑写原生 App 或小程序。

### 8.4 推送

| 方案 | 平台 | 成本 | 备注 |
| --- | --- | --- | --- |
| Bark | iOS | 免费/自建 | 极简单，一个 HTTP GET 就推送 |
| ntfy | Android/iOS | 免费/自建 | 开源，支持自建服务器 |
| Telegram Bot | 全平台 | 免费 | 国内直连不稳，需代理 |
| 企业微信/钉钉机器人 | 全平台 | 免费 | 国内稳定，适合自己用 |

> 建议：**Bark（iOS）或 ntfy（Android）**，Node-RED 里一个 http request 节点搞定。延迟通常在 1 s 内。

### 8.5 端到端时延测量

每条消息带 `ts`（毫秒）。Node-RED 里收到事件时打时间戳，算出 `t_recv - t_evt`，存到文件。跑 20 次看 P95——这就是 V4 的验收数据。

## 9. 定位与地图

- **优先用模组内置 GNSS**（§3.2），NMEA 用 `TinyGPSPlus` 解析。
- **冷启动很慢**（30–90 s），热启动 5–15 s。原型阶段可以做"定时热启动"：每 10 min 唤醒 GNSS 30 s，保持星历新鲜。
- **车架遮挡**：原型阶段先把 GNSS 天线**吸盘/贴片装在车座下方朝上**，别一开始就塞进金属管里，否则你会误判"GPS 不行"。
- **地图展示**：Node-RED 的 worldmap 用 OSM，国内加载慢但能用；真要好看就换高德静态图 URL（把经纬度拼进链接）。
- **兜底**：GNSS 无定位时上报最后一次有效位置 + 时间戳，APP/面板上标注"最后已知位置"。

## 10. 外壳与装车

**任务分解与验收见 [硬件任务清单 B/C/D 节](hardware-checklist.md#b-机械设计)**，这里只留原型阶段的建模思路。

| 项 | 原型做法 |
| --- | --- |
| 设计 | OpenSCAD 参数化，改一个管径参数出模型 |
| 打印 | FDM，PETG（好打、耐候）或 ASA（抗 UV 但翘边） |
| 内衬 | 2 mm TPU/EVA 泡棉，减震 + 防刮漆 |

**一体机之后的装车位置变了**：不再是"贴车架"，而是用 M5 水壶架孔固定整块锁体，锁环绕后轮。位置校核见 [H-M-01](hardware-checklist.md#b-机械设计)。

参数化外壳的骨架（早期"贴管"方案，可作为适配件参考）：

```scad
d = 31.8;          // 车架管径
wall = 2.4;        // 壁厚
inner = d/2 + 1.2; // 内半径 + 泡棉
difference() {
  union() {
    cylinder(h=110, r=inner+wall, $fn=96);
    translate([0,-inner-wall*0.8,0]) cube([40, inner*2+wall*1.6, 110], center=true);
  }
  cylinder(h=120, r=inner, $fn=96, center=true);
  // 电路仓、喇叭孔、扎带槽另加
}
```

- [ ] 待机（10 min 心跳）实测电流，推算天数

## 13. 已知的坑（提前避）

| # | 坑 | 现象 | 对策 |
| --- | --- | --- | --- |
| 1 | 喇叭打崩电源 | 响一声就重启 | 大电容 + 粗细线 + 错峰 |
| 2 | IP5306 小电流关机 | 待机几分钟断电 | 换 TP4056/ETA6098 |
| 3 | 4G 模组吃电流 | 电压跌到 3.2 V 以下 | 电池直供模组，别过升压 |
| 4 | 串口被日志占满 | 模组 AT 无响应 | 用第二路 UART，或把日志转 USB CDC |
| 5 | GNSS 塞进金属车架 | 永远定不上位 | 天线朝上、远离金属，先外置 |
| 6 | 音频爆音 | 播放开始/结束"啪"一声 | 功放使能脚做软启停 |
| 7 | 误报毁掉信心 | 半夜乱叫 | **影子模式先跑一周** |
| 8 | 电池过热 | 夏天车内 60 °C+ | NTC 监控 + 降额 + 别密封死 |
| 9 | MQTT 断线不重连 | 设备"假在线" | 心跳 + LWT（遗嘱消息） |
| 10 | 时间戳漂移 | 事件时间对不上 | 4G 联网后 NTP 校时，本地 RTC 兜底 |
